Documento de Diseño

Comparador de Planes de Gobierno
Perú 2026

Cómo funciona el sistema que permite consultar y comparar las propuestas de los 7 planes de gobierno presentados ante el JNE, citando siempre candidato y página fuente.

Prueba de concepto — esta versión cubre las Elecciones Generales 2026, pero el diseño está pensado para escalar a las Elecciones Regionales y Municipales, donde el número de candidatos y planes locales es mucho mayor.
Visión General

¿Qué es este proyecto?

Una app de consulta ciudadana con dos modos de uso: preguntas libres sobre un candidato o el conjunto de planes, y comparación de un tema específico entre varios candidatos a la vez.

Modo Chat

Pregunta libre. Recupera los 10 fragmentos más relevantes (global o filtrado por candidato) y responde citando página.

Modo Comparar

Un tema corto. Retrieval independiente por candidato (top-4 cada uno) para no sesgar por extensión del documento.

Sin servidor con datos

La API key de OpenRouter la pega cada usuario en el navegador y vive solo en localStorage, nunca en el servidor.

Cómo funciona el modo Comparar

La diferencia clave: el retrieval se hace por separado para cada candidato, para que un plan de 145 páginas no opaque a uno de 25.

sequenceDiagram
    actor U as Ciudadano
    participant FE as Frontend
    participant API as API Route
(/api/compare)
    participant IDX as VectorIndex

    U->>FE: Escribe tema (ej. "seguridad ciudadana")
    FE->>API: POST {apiKey, tema, candidatos[]}
    API->>API: embedQuery(tema)

    loop por cada candidato seleccionado
        API->>IDX: search(vector, topK=4, filtro=[candidato])
        IDX-->>API: top-4 fragmentos de ESE candidato
    end

    API->>API: agrupar contexto por candidato
    API->>API: LLM devuelve array JSON:
[{candidato, partido, propuesta, sin_informacion}]
    API-->>FE: tarjetas de propuesta, una por candidato
    FE-->>U: Grilla comparativa con citas de página
Estructura

Capas de la arquitectura

1

Frontend (Next.js App Router)

CSS plano en app/globals.css, sin librerías de UI externas. El usuario pega su API key de OpenRouter (guardada solo en localStorage), elige modo chat o comparar, y opcionalmente filtra por candidato.

2

API Routes (orquestación)

app/api/chat/route.ts y app/api/compare/route.ts reciben la pregunta, generan el embedding, buscan en el índice en memoria y arman el prompt para el LLM. Cada request corre en una función serverless de Vercel.

3

Índice vectorial en memoria

lib/index.ts construye un singleton de VectorIndex (lib/embeddings.ts) a partir de data/chunks.json: 2,019 fragmentos ya con su embedding precalculado. Solo se calcula el embedding de la pregunta en cada request.

4

OpenRouter (servicios externos)

Un único proveedor para dos tareas: openai/text-embedding-3-small (512 dimensiones) para los embeddings, y openai/gpt-4o-mini (modelo fijo, MODELO_FIJO) para generar la respuesta final.

Datos

De los PDF del JNE a fragmentos citables

Pipeline offline, ejecutado una sola vez (y de nuevo solo si cambian las fuentes):

PasoScriptQué hace
1. Extracción extract_chunks_md.py Lee fuentes-oficiales/*.md, detecta marcadores de página, limpia markdown y segmenta en chunks de 900 caracteres con 150 de overlap.
2. Embeddings scripts/build-embeddings.mjs Agrega el campo embedding a cada chunk vía OpenRouter. Resumible si se corta a mitad de camino.
3. Resultado data/chunks.json 2,019 chunks con texto, candidato, partido, página y embedding — listo para servir en producción sin recalcular nada.

Alcance y proyección

Una prueba de concepto pensada para escalar

Esta versión demuestra el enfoque con los 7 planes de gobierno de las Elecciones Generales 2026. La arquitectura — chunking + embeddings + índice en memoria, sin base de datos ni servidor con estado — está pensada desde el inicio para escalar a un escenario de mayor volumen: las Elecciones Regionales y Municipales, donde el número de candidatos y planes de gobierno locales es varios órdenes de magnitud mayor (cientos de gobiernos regionales, provinciales y distritales, cada uno con su propio plan).

→

Mismo pipeline, más fuentes

extract_chunks_md.py y scripts/build-embeddings.mjs no asumen nada específico de la elección general — solo esperan markdown con marcadores de página. Agregar planes regionales/municipales es correr el mismo pipeline sobre más archivos.

→

Retrieval que ya no depende de cargar todo en memoria

Con cientos de planes, data/chunks.json cargado completo en cada invocación serverless dejaría de ser viable. El siguiente paso natural sería mover el índice a una base vectorial (ej. Pinecone) en vez de un VectorIndex en memoria.

→

Filtro por ámbito geográfico

El filtro actual por candidato se extendería a un filtro por región, provincia o distrito, para que la pregunta "¿qué propone el candidato a la municipalidad de X?" busque solo dentro de ese ámbito.

Límites conocidos

Qué no resuelve (todavía)

!

Nombres propios vs. tema semántico

Preguntar "¿qué propone Jorge Nieto sobre IA?" sin usar el filtro de candidato mezcla fragmentos de otros candidatos, porque los embeddings no distinguen bien nombres propios. Con el filtro de candidato activado, la respuesta es correcta.

!

Extensión desigual de los documentos

Los planes van de 25 a 145 páginas. El modo comparativo lo mitiga haciendo retrieval independiente por candidato en vez de una búsqueda global.
